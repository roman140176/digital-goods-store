# Магазин цифровых товаров — тестовое задание

Витрина и бэкенд магазина ключей, пополнений, подписок и подарочных карт.
Задача решалась вокруг главного требования: **ключ выдаётся ровно один раз**
при двойных кликах, повторных и одновременных вебхуках, а сбои переводят заказ
в восстановимое состояние, а не роняют систему.

- **Бэкенд:** PHP 8.3, Laravel 12, PostgreSQL 16, очередь на базе, php-fpm за nginx
- **Фронтенд:** TypeScript + Vite, без фреймворка, SCSS
- **Инфраструктура:** Docker Compose — приложение, воркер, планировщик, база, nginx и два независимых поставщика

## Запуск

Нужен только Docker (PHP и Node на хосте не требуются — фронт собирается в контейнере).

```bash
make up
```

Команда сама создаёт `backend/.env` из шаблона, генерирует ключ приложения,
собирает витрину, поднимает контейнеры и накатывает схему с данными из ТЗ.

После запуска:

| что | адрес |
|---|---|
| витрина | http://localhost:8085 |
| админка «оплачено, но не выдано» | http://localhost:8085/admin/orders?token=admin-secret-token |
| склад поставщика A | http://localhost:8086/inventory |
| склад поставщика B | http://localhost:8087/inventory |

Остальные команды: `make help`.

## Как воспроизвести проверку гонок

```bash
make race-all
```

Команда пересоздаёт схему, засевает исходные данные из ТЗ, возвращает склады
поставщиков в начальное состояние и прогоняет семь состязательных сценариев.
Каждый сценарий печатает PASS/FAIL по каждой проверке, в конце — сводная таблица.
Отдельный сценарий запускается своей целью, например `make race-timeout-leak`.

Параллельность настоящая: запросы залпа уходят одним `curl_multi`-хэндлом
одновременно, а не по очереди. Проверки идут не по «средним» счётчикам, а по
конкретному заказу: у поставщика спрашивается, сколько ключей закреплено за
его `request_id`, и это число обязано быть равно единице.

| сценарий | что проверяет | критерий ТЗ |
|---|---|---|
| `race-double-click` | 20 одновременных заказов с одним `Idempotency-Key` → один заказ | двойной клик «Купить» |
| `race-webhook-same-event` | 50 одновременных вебхуков с одним `event_id` | 1, 2 |
| `race-webhook-distinct-events` | 50 одновременных вебхуков с разными `event_id` по одному заказу | 1 |
| `race-out-of-order` | вебхук раньше заказа; устаревшее и запоздавшее события | 3 |
| `race-empty-pool` | пустой склад → восстановимое состояние → пополнение → 10 одновременных повторных выдач | 4 |
| `race-promo-limit` | `ONCEONLY` и `LIMIT3` под 50 одновременными заказами | 5 |
| `race-timeout-leak` | поставщик выдал код, но ответ не дошёл | ловушка таймаута из контракта |

Модульные и функциональные тесты: `make test` (34 теста, 130 проверок).
Они идут на PostgreSQL, потому что схема и логика опираются на его возможности —
частичные уникальные индексы, `FOR UPDATE SKIP LOCKED`, `ON CONFLICT`.

## Чем обеспечена однократная выдача

Коротко: **гарантии живут в ограничениях базы, а не в проверках на уровне кода.**
Однократность не зависит ни от порядка запросов, ни от числа воркеров, ни от того,
сколько раз платёжная система повторит доставку.

| ограничение | что закрывает |
|---|---|
| `orders.idempotency_key UNIQUE` | двойной клик «Купить» даёт один заказ: вторая вставка уходит в конфликт, и клиент получает тот же заказ |
| `payment_events.event_id PRIMARY KEY` | повторный вебхук не доходит до бизнес-логики вообще |
| `SELECT ... FOR UPDATE` на заказе + машина состояний | из `created` выйти может ровно одно из параллельных событий |
| `deliveries.order_id UNIQUE` | на заказ приходится максимум одна выдача |
| `deliveries.request_id UNIQUE` + карта `request_id → код` у поставщика | повтор после сбоя возвращает тот же код, а не расходует второй ключ |
| `keys.request_id UNIQUE` в базе поставщика | один ключ физически не может быть закреплён за двумя запросами |
| частичный `UNIQUE (delivered_code)` | один код не может оказаться в двух заказах магазина |
| `UPDATE promocodes SET used_count = used_count + 1 WHERE used_count < max_uses` | лимит промокода соблюдается по числу затронутых строк, без «прочитать-сравнить-записать» |

### Ловушка таймаута

Самое тонкое место задания. Поставщик идемпотентен по `request_id`, и из этого
следует важное различие:

- **ответ получен, кода в нём нет** — значит код и не выдавался: идемпотентный
  поставщик вернул бы сохранённый код, если бы он существовал. Переход к
  резервному поставщику безопасен;
- **ответа не было вовсе (таймаут)** — код мог быть выдан, а подтверждение
  потеряться. Переход к резервному поставщику здесь израсходовал бы **второй
  ключ**, поэтому он запрещён: заказ уходит в восстановимое состояние, а
  повторы идут тому же поставщику с тем же `request_id`, пока он не ответит.

Это поведение закрыто и тестом (`IssueOrderCodeTest`), и живым сценарием
`make race-timeout-leak`, где поставщик A настроен выдавать код и не отвечать.

## Архитектура

```
    браузер
       │  POST /api/orders  (Idempotency-Key)
       ▼
    ┌──────────────┐   вебхук по контракту   ┌──────────────────┐
    │  nginx + app │◄────────────────────────│ эмулятор оплаты  │
    └──────┬───────┘                         └──────────────────┘
           │ статус created → paid, одна строка выдачи, задача в очередь
           ▼
    ┌──────────────┐        POST /issue      ┌──────────────┐
    │    worker    │────────────────────────►│ поставщик A  │ свой склад
    │              │  (тот же request_id)    └──────────────┘
    │              │        только при                        
    │              │      однозначном отказе ┌──────────────┐
    │              │────────────────────────►│ поставщик B  │ свой склад
    └──────┬───────┘                         └──────────────┘
           │ delivered / out_of_stock / delivery_failed
           ▼
    ┌──────────────┐
    │  scheduler   │ раз в минуту дожимает незавершённые события и выдачи
    └──────────────┘
```

Ключевые решения:

- **Вебхук отвечает быстро и почти всегда `200`.** Дубли и нарушенный порядок —
  это норма контракта, а не ошибка. `5xx` возвращается только при настоящем сбое,
  чтобы платёжная система повторила доставку.
- **Выдача асинхронная.** Поставщик по условиям задачи умеет подвисать, а вебхук
  обязан ответить быстро, поэтому обращение к поставщику живёт в очереди.
- **Порядок событий определяется меткой платёжной системы**, а не временем
  доставки вебхука: заказ хранит `last_event_at`, и событие старше применённого
  отбрасывается как устаревшее.
- **Прерванная обработка события доводится до конца.** Если событие записалось,
  а применение упало, повторная доставка не считается дублем — иначе оплата
  потерялась бы навсегда. Такие записи добирает и планировщик.
- **Склады поставщиков лежат в отдельных базах.** Приложение не имеет к пулу
  ключей доступа и ходит только через HTTP-контракт `/issue`.
- **Уникальность задачи в очереди намеренно не используется.** Гарантия должна
  держаться на базе, а не на инфраструктуре очереди: даже при дублировании
  задачи или нескольких воркерах второй ключ не уйдёт.
- **Заказ не «падает».** `out_of_stock` и `delivery_failed` — рабочие состояния,
  из которых выдача продолжается автоматически или вручную из админки.

Статусы заказа и переходы — по модели из ТЗ: `created → paid → delivering →
delivered`, ветки `payment_failed`, `out_of_stock`, `delivery_failed`.
Состояние `delivered` не отменяется ничем.

## API

| метод | адрес | назначение |
|---|---|---|
| `GET` | `/api/products` | каталог |
| `POST` | `/api/orders` | создание заказа, обязателен заголовок `Idempotency-Key` |
| `GET` | `/api/orders/{id}` | статус, выданный код и история переходов |
| `POST` | `/api/webhook/payment` | вебхук платёжной системы по контракту ТЗ |
| `POST` | `/api/dev/pay/{id}?result=success\|fail` | эмулятор оплаты: формирует событие и отправляет вебхук |
| `POST` | `/api/dev/orders` | заказ с заранее известным id — только для сценария «вебхук раньше заказа», недоступно в production |
| `GET` | `/admin/orders?token=` | список «оплачено, но не выдано» |
| `POST` | `/admin/orders/{id}/redeliver` | безопасная повторная выдача |
| `POST` | `/admin/suppliers/{a\|b}/restock` | пополнение склада поставщика |

Поставщики (заглушки по контракту ТЗ): `POST /issue`, `GET /inventory`,
`GET /issued/{request_id}`, `POST /restock`, `POST /drain`, `POST /reset`,
`POST /config` — последняя задаёт долю отказов, таймаутов и режим
«выдал код, но не ответил».

## Витрина

Сверстана верхняя часть макета: шапка, баннер-карусель, ряд иконок сервисов,
блок пополнения Steam, один ряд карточек товара. Отзывы и футер, по ТЗ, не
верстались. Геометрия снята из макета и совпадает с ним: полотно 1280,
контейнер 1200, шапка 80, баннер 1200×263 с вырезанным углом 98×48 под пилюлю
со стрелками, карточки 227 с шагом 16, сайдбар меню 320, панель меню 584.

Обязательный интерактив (номера со скриншота ТЗ):

1. **Баннер-карусель** — автопрокрутка, стрелки, активная точка-индикатор;
   пауза при наведении и при уходе со вкладки, уважает `prefers-reduced-motion`.
2. **Кнопка «Каталог»** — открывает меню, закрывается повторным кликом, кликом
   вне меню и клавишей Escape; при открытии поиск переходит в активное
   состояние, как на втором скриншоте ТЗ.
3. **Переключатель валют `$ ₸ ₽`** — меняется активное состояние; пересчёт
   суммы, по ТЗ, не делается.
4. **Иконки сервисов** — плавное выделение при наведении.
5. **Карточки товара** — подъём, тень и обводка при наведении.

Покупка начинается кнопкой «Купить» на карточке: фронт создаёт заказ с ключом
идемпотентности и уводит на страницу статуса, которая опрашивает API раз в
секунду и показывает выданный код и историю переходов.

## Допущения

- Пул из 50 ключей ТЗ универсален: сопоставления `sku` → ключ в задании нет.
  Пул поделён между поставщиками, A получает 30 ключей, B — 20; доли задаются
  переменными `KEYS_OFFSET` и `KEYS_LIMIT`.
- Деньги хранятся целыми в копейках (`*_minor`), без чисел с плавающей точкой.
  Цену и скидку клиент не присылает никогда — только `sku` и промокод.
- Промокод занимает использование в момент создания заказа и освобождает его
  при неуспешной оплате. Строка списания не удаляется: в аудите остаётся, что
  код применялся и был возвращён.
- Вебхук на несуществующий заказ получает `200` и паркуется: восстановлением
  владеет магазин, заставлять платёжную систему повторять доставку незачем.
- Рассинхрон валют в блоке Steam (сумма в ₽, кнопка в $) оставлен как в макете —
  ТЗ просит его не исправлять.
- Зачёркнутая цена на карточке декоративная: старой цены в данных ТЗ нет,
  она считается от текущей, чтобы не ломать вёрстку.
- Баннер в макете пустой, готового арта нет ни в исходнике, ни на скриншотах.
  Слайды собраны кропами имеющегося изображения и описаны данными
  (`frontend/src/data/slides.ts`) — тематические баннеры подставляются заменой
  путей, без правки вёрстки.
- Контейнеры приложения запускаются под текущим пользователем (`make` передаёт
  `id -u`/`id -g`), чтобы `storage/` оставался доступен для записи и на хосте,
  и в контейнере.

## Что не делалось

По прямым указаниям ТЗ: реальный эквайринг, проверка подписи вебхука,
авторизация (у админки простой токен), отзывы, футер, мобильная и тёмная
версии, дизайн страницы статуса и админки, пересчёт валют, детальная точность
колонок меню каталога.

## Затраченное время

Около 14 часов: примерно 5 на надёжность выдачи и состязательные сценарии,
4 на вёрстку и интерактив витрины, 3 на инфраструктуру и заглушки поставщиков,
2 на тесты и описание решений.
