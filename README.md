# Магазин цифровых товаров — тестовое задание

Витрина и бэкенд магазина ключей, пополнений, подписок и подарочных карт.
Задача решалась вокруг главного требования: **ключ выдаётся ровно один раз**
при двойных кликах, повторных и одновременных вебхуках, а сбои переводят заказ
в восстановимое состояние, а не роняют систему.

- **Бэкенд:** PHP 8.3, Laravel 12, PostgreSQL 16, очередь на базе, php-fpm за nginx
- **Фронтенд:** TypeScript + Vite, без фреймворка, SCSS
- **Инфраструктура:** Docker Compose — приложение, воркер, планировщик, база, nginx и два независимых поставщика

## Запуск

Нужен только Docker (PHP и Node на хосте не требуются — фронт собирается в контейнере).

```bash
make up
```

Команда сама создаёт `backend/.env` из шаблона, генерирует ключ приложения,
собирает витрину, поднимает контейнеры и накатывает схему с данными из ТЗ.

После запуска:

| что | адрес |
|---|---|
| витрина | http://localhost:8085 |
| админка «оплачено, но не выдано» | http://localhost:8085/admin/orders?token=admin-secret-token |
| склад поставщика A | http://localhost:8086/inventory |
| склад поставщика B | http://localhost:8087/inventory |

Остальные команды: `make help`.

## Как воспроизвести проверку гонок

```bash
make race-all
```

Команда пересоздаёт схему, засевает исходные данные из ТЗ, возвращает склады
поставщиков в начальное состояние и прогоняет восемь состязательных сценариев
(74 проверки). Каждый сценарий печатает PASS/FAIL по каждой проверке, в конце —
сводная таблица. Отдельный сценарий запускается своей целью, например
`make race-timeout-leak`.

Сценарии расходуют пул ключей и лимиты промокодов, поэтому перед ручной
демонстрацией витрины состояние стоит вернуть в исходное: `make fresh`
(чистая схема, данные ТЗ, склады поставщиков заново).

Параллельность настоящая: запросы залпа уходят одним `curl_multi`-хэндлом
одновременно, а не по очереди. Проверки идут не по «средним» счётчикам, а по
конкретному заказу: у поставщика спрашивается, сколько ключей закреплено за
его `request_id`, и это число обязано быть равно единице.

| сценарий | что проверяет | критерий ТЗ |
|---|---|---|
| `race-double-click` | 20 одновременных заказов с одним `Idempotency-Key` → один заказ | двойной клик «Купить» |
| `race-webhook-same-event` | 50 одновременных вебхуков с одним `event_id` | 1, 2 |
| `race-webhook-distinct-events` | 50 одновременных вебхуков с разными `event_id` по одному заказу | 1 |
| `race-out-of-order` | вебхук раньше заказа; устаревшее и запоздавшее события | 3 |
| `race-empty-pool` | пустой склад → восстановимое состояние → пополнение → 10 одновременных повторных выдач | 4 |
| `race-promo-limit` | `ONCEONLY` и `LIMIT3` под 50 одновременными заказами | 5 |
| `race-timeout-leak` | поставщик выдал код, но ответ не дошёл | ловушка таймаута из контракта |
| `race-error-after-issue` | поставщик закрепил ключ и ответил `503` при полном складе резервного | ловушка таймаута из контракта |

Модульные и функциональные тесты: `make test` (44 теста, 183 проверки).
Они идут на PostgreSQL, потому что схема и логика опираются на его возможности —
частичные уникальные индексы, `FOR UPDATE SKIP LOCKED`, `ON CONFLICT`.

## Чем обеспечена однократная выдача

Коротко: **гарантии живут в ограничениях базы, а не в проверках на уровне кода.**
Однократность не зависит ни от порядка запросов, ни от числа воркеров, ни от того,
сколько раз платёжная система повторит доставку.

| ограничение | что закрывает |
|---|---|
| `orders.idempotency_key UNIQUE` | двойной клик «Купить» даёт один заказ: вторая вставка уходит в конфликт, и клиент получает тот же заказ |
| `payment_events.event_id PRIMARY KEY` | повторный вебхук не доходит до бизнес-логики вообще |
| `SELECT ... FOR UPDATE` на заказе + машина состояний | из `created` выйти может ровно одно из параллельных событий |
| `deliveries.order_id UNIQUE` | на заказ приходится максимум одна выдача |
| `deliveries.request_id UNIQUE` + карта `request_id → код` у поставщика | повтор после сбоя возвращает тот же код, а не расходует второй ключ |
| `keys.request_id UNIQUE` в базе поставщика | один ключ физически не может быть закреплён за двумя запросами |
| частичный `UNIQUE (delivered_code)` | один код не может оказаться в двух заказах магазина |
| `UPDATE promocodes SET used_count = used_count + 1 WHERE used_count < max_uses` | лимит промокода соблюдается по числу затронутых строк, без «прочитать-сравнить-записать» |

### Ловушка таймаута

Самое тонкое место задания. Уйти к резервному поставщику можно **только по
однозначному ответу «ключей нет»** (`out_of_stock`). Всё остальное — таймаут,
`5xx`, недоступность, непонятная причина — это неизвестность: код мог быть уже
закреплён за `request_id`, а ответ его не донёс. Переход к резервному в такой
ситуации израсходовал бы **второй ключ**, поэтому он запрещён: заказ уходит в
восстановимое состояние, а повторы идут тому же поставщику с тем же
`request_id`, пока он не ответит внятно.

Соблазнительное правило «ответ получен, кода в нём нет — значит кода не
существует» **неверно**, и это ровно та ошибка, которую нашло состязательное
ревью: поставщик может закрепить ключ и упасть уже на ответе. Заглушка это
воспроизводит режимом `issue_then_error`, и до правки за одним заказом
оказывалось два ключа — свой и резервного поставщика.

Поведение закрыто тестами (`IssueOrderCodeTest`) и двумя живыми сценариями:
`make race-timeout-leak` (A выдаёт код и не отвечает) и
`make race-error-after-issue` (A закрепляет ключ и отвечает `503`, при этом у
резервного поставщика полный склад).

## Архитектура

```
    браузер
       │  POST /api/orders  (Idempotency-Key)
       ▼
    ┌──────────────┐   вебхук по контракту   ┌──────────────────┐
    │  nginx + app │◄────────────────────────│ эмулятор оплаты  │
    └──────┬───────┘                         └──────────────────┘
           │ статус created → paid, одна строка выдачи, задача в очередь
           ▼
    ┌──────────────┐        POST /issue      ┌──────────────┐
    │    worker    │────────────────────────►│ поставщик A  │ свой склад
    │              │  (тот же request_id)    └──────────────┘
    │              │        только при                        
    │              │      однозначном отказе ┌──────────────┐
    │              │────────────────────────►│ поставщик B  │ свой склад
    └──────┬───────┘                         └──────────────┘
           │ delivered / out_of_stock / delivery_failed
           ▼
    ┌──────────────┐
    │  scheduler   │ раз в минуту дожимает незавершённые события и выдачи
    └──────────────┘
```

Ключевые решения:

- **Вебхук отвечает быстро и почти всегда `200`.** Дубли и нарушенный порядок —
  это норма контракта, а не ошибка. `5xx` возвращается только при настоящем сбое,
  чтобы платёжная система повторила доставку.
- **Выдача асинхронная.** Поставщик по условиям задачи умеет подвисать, а вебхук
  обязан ответить быстро, поэтому обращение к поставщику живёт в очереди.
- **Порядок событий определяется меткой платёжной системы**, а не временем
  доставки вебхука: заказ хранит `last_event_at`, и событие старше применённого
  отбрасывается как устаревшее.
- **Прерванная обработка события доводится до конца.** Если событие записалось,
  а применение упало, повторная доставка не считается дублем — иначе оплата
  потерялась бы навсегда. Такие записи добирает и планировщик.
- **Склады поставщиков лежат в отдельных базах.** Приложение не имеет к пулу
  ключей доступа и ходит только через HTTP-контракт `/issue`.
- **Уникальность задачи в очереди намеренно не используется.** Гарантия должна
  держаться на базе, а не на инфраструктуре очереди: даже при дублировании
  задачи или нескольких воркерах второй ключ не уйдёт.
- **Заказ не «падает».** `out_of_stock` и `delivery_failed` — рабочие состояния,
  из которых выдача продолжается автоматически или вручную из админки.

Статусы заказа и переходы — по модели из ТЗ: `created → paid → delivering →
delivered`, ветки `payment_failed`, `out_of_stock`, `delivery_failed`.
Состояние `delivered` не отменяется ничем.

## API

| метод | адрес | назначение |
|---|---|---|
| `GET` | `/api/products` | каталог |
| `POST` | `/api/orders` | создание заказа, обязателен заголовок `Idempotency-Key` |
| `GET` | `/api/orders/{id}` | статус, выданный код и история переходов |
| `POST` | `/api/webhook/payment` | вебхук платёжной системы по контракту ТЗ |
| `POST` | `/api/dev/pay/{id}?result=success\|fail` | эмулятор оплаты: формирует событие и отправляет вебхук |
| `POST` | `/api/dev/orders` | заказ с заранее известным id — только для сценария «вебхук раньше заказа», недоступно в production |
| `GET` | `/admin/orders?token=` | список «оплачено, но не выдано» |
| `POST` | `/admin/orders/{id}/redeliver` | безопасная повторная выдача |
| `POST` | `/admin/suppliers/{a\|b}/restock` | пополнение склада поставщика |

Поставщики (заглушки по контракту ТЗ): `POST /issue`, `GET /inventory`,
`GET /issued/{request_id}`, `POST /restock`, `POST /drain`, `POST /reset`,
`POST /config` — последняя задаёт долю отказов, таймаутов и режим
«выдал код, но не ответил».

## Витрина

ТЗ просило верхнюю часть до первого ряда карточек. Сверстана страница целиком —
шапка, баннер-карусель, ряд иконок сервисов, блок пополнения Steam, три ряда
карточек товара, блок последних отзывов и футер: отзывы и футер сделаны сверх
задания, по своей инициативе.

Значения не подбирались на глаз — размеры, отступы, радиусы, тени, шрифты и
цвета взяты из макета через Figma MCP (design context) по каждому узлу.
Контрольные точки после вёрстки совпадают с макетом: полотно 1280, контейнер
1200, шапка 80 с границей `#f2f4f7`, кнопка каталога 232/18 120×44, поиск
428/18 688×44 (чёрная подложка и белое поле 642×40 внутри), профиль 1196/18
44×44, баннер 40/96 1200×263, пилюля стрелок 1150/96 90×40, блок сервисов
40/375 1200×253, плитка иконки 72×72 в обёртке 76 с брендовой рамкой 2px,
разделитель 1160×1 на y=519, ряд пополнения 285.51 / 284.77 / 341.72 / 200,
карточка 227.27 с медиа 151.72, отзыв 389.33, футер 1200×234.

Шрифт макета — Montserrat. Он лежит в репозитории (вариативный woff2,
кириллица и латиница, 60 КБ) и не тянется с внешнего CDN, поэтому витрина
одинаково выглядит и без интернета. Иконки — экспортированные из Figma SVG и
PNG, пережатые в webp; ничего не перерисовано вручную.

Меню каталога сверстано по второму скриншоту ТЗ: панель во всю ширину полотна,
сайдбар 320 с активной категорией, пять колонок платформ по 137.6 с гапом 32 и
вторым рядом «Подборки».

Обязательный интерактив (номера со скриншота ТЗ):

1. **Баннер-карусель** — автопрокрутка, стрелки, активная точка-индикатор;
   пауза при наведении и при уходе со вкладки, уважает `prefers-reduced-motion`.
2. **Кнопка «Каталог»** — открывает меню, закрывается повторным кликом, кликом
   вне меню и клавишей Escape. Вид поиска при этом не меняется: в макете
   закрытое и открытое состояния шапки идентичны.
3. **Переключатель валют `$ ₸ ₽`** — меняется активное состояние; пересчёт
   суммы, по ТЗ, не делается.
4. **Иконки сервисов** — плавное выделение при наведении.
5. **Карточки товара** — подъём, тень и обводка при наведении.

Покупка начинается кнопкой «Купить» на карточке: фронт создаёт заказ с ключом
идемпотентности и уводит на страницу статуса, которая опрашивает API (интервал
растёт до 5 секунд, опрос замолкает на скрытой вкладке) и показывает выданный
код и историю переходов.

Промокод этапа 4 живёт там, где он есть в макете: кнопка «Ввести промокод» в
блоке пополнения Steam раскрывает поле, а кнопка «Оплатить» покупает товар
каталога `STEAM-TOPUP-500` — именно этот номинал нарисован в блоке. Скидку
считает сервер, клиент присылает только код; отказ по коду («не найден»,
«лимит исчерпан») показывается у поля.

## Допущения

- Пул из 50 ключей ТЗ универсален: сопоставления `sku` → ключ в задании нет.
  Пул поделён между поставщиками, A получает 30 ключей, B — 20; доли задаются
  переменными `KEYS_OFFSET` и `KEYS_LIMIT`.
- Деньги хранятся целыми в копейках (`*_minor`), без чисел с плавающей точкой.
  Цену и скидку клиент не присылает никогда — только `sku` и промокод.
- Промокод занимает использование в момент создания заказа и **не освобождает
  его при неуспешной оплате**. Это осознанный выбор: платёж может подтвердиться
  позже (заказ обязан ожить, иначе оплата теряется), и если слот к тому времени
  уйдёт другому покупателю, код окажется применён больше `max_uses` раз. Слот
  принадлежит заказу, а не попытке оплаты: повторная оплата того же заказа
  сохраняет скидку. Цена решения — брошенный неоплаченный заказ держит своё
  использование; `make fresh` возвращает лимиты в исходное состояние.
- Вебхук на несуществующий заказ получает `200` и паркуется: восстановлением
  владеет магазин, заставлять платёжную систему повторять доставку незачем.
  Припаркованное событие **не считается обработанным** — его применяет либо
  создание заказа, либо планировщик, когда заказ появится. Иначе гонка
  «вебхук и создание заказа одновременно» теряла бы оплату.
- Порядок событий определяет метка платёжной системы, а в контракте она с
  секундной точностью. На ничьей побеждает `paid`: потерять деньги хуже, чем
  лишний раз оживить заказ, а оживление безопасно.
- Рассинхрон валют в блоке Steam (сумма в ₽, кнопка в $) оставлен как в макете —
  ТЗ просит его не исправлять.
- Зачёркнутая цена на карточке декоративная: старой цены в данных ТЗ нет,
  она считается от текущей, чтобы не ломать вёрстку.
- Каталог ТЗ содержит 12 товаров, а в макете три ряда по пять карточек,
  поэтому ряды заполняются по кругу — три плитки повторяются.
- Названия карточек оформлены эмодзи-акцентами, как в макете
  (`💥 DOOM 2016 💀 STEAM KEY 🔑`), но по названиям товаров из каталога ТЗ.
  Квалификатор вроде «STEAM KEY» не добавляется: с ним ни одно название
  каталога не влезает в строку 200.92px, а в макете название занимает одну
  строку, регион — вторую.
- Один код не может оказаться в двух заказах: это частичный `UNIQUE` по
  `delivered_code`. Если поставщика заставить вернуть код, уже привязанный к
  другому заказу (штатно так делает только `POST /reset` заглушки, который
  возвращает выданные ключи в сток), выдача такого заказа будет падать на
  ограничении — состояние лечится общим сбросом `make fresh`.
- Баннер в макете пустой, готового арта нет ни в исходнике, ни на скриншотах.
  Слайды собраны кропами имеющегося изображения и описаны данными
  (`frontend/src/data/slides.ts`) — тематические баннеры подставляются заменой
  путей, без правки вёрстки.
- Контейнеры приложения запускаются под текущим пользователем (`make` передаёт
  `id -u`/`id -g`), чтобы `storage/` оставался доступен для записи и на хосте,
  и в контейнере.

## Что не делалось

По прямым указаниям ТЗ: реальный эквайринг, проверка подписи вебхука,
авторизация (у админки простой токен), мобильная и тёмная версии, дизайн
страницы статуса и админки, пересчёт валют.

## Затраченное время

Примерно 4 часа чистого времени. Скорость — следствие инструментов и
организации работы, а не срезанных углов, поэтому ниже прямо описано, как
задача делалась.

Инструмент — **Claude Opus 5** в режиме агентного воркфлоу: не «сгенерируй
магазин», а несколько управляемых потоков с моей постановкой, приёмкой и
правками на каждом шаге. Архитектурные решения — где живёт гарантия
однократности, что держит база, а что код — мои, и я отвечаю за каждое.

- **Постановка до кода.** Сначала брейншторм требований и рисков:
  однократная выдача, ловушка таймаута поставщика, порядок вебхуков, лимит
  промокода под параллелизмом. Спецификация, модель статусов и план по
  этапам согласованы до первой строки кода.
- **Оркестрация вместо линейной разработки.** Независимые части — схема и
  ограничения PostgreSQL, заглушки поставщиков, витрина, состязательные
  скрипты — шли параллельными потоками по общей спецификации, с профильным
  агентом на каждый слой.
- **Вёрстка.** Отдельный агент с заданными скилами, настроенный под
  энтерпрайз-проекты, в которых я работаю: тот же стек, те же соглашения по
  структуре и стилям. Макет читался через **Figma MCP** — размеры, отступы,
  типографика и цвета берутся из узлов макета, иконки экспортируются
  ассетами, а не перерисовываются. Результат сверялся измерениями в
  браузере, а не сравнением скриншотов.
- **Проверка в несколько независимых проходов.** Модульные и функциональные
  тесты (44 теста, 183 проверки), состязательные сценарии (`make race-all` —
  8 сценариев, 74 проверки), затем adversarial-ревью: независимые параллельные
  проходы, чья единственная задача — сломать однократность выдачи,
  восстановление после сбоев и денежную логику. Именно оно поймало три
  дефекта, которых не видели ни тесты, ни состязательные сценарии:
  - **задвоение ключа.** Ответ `503` от поставщика после того, как ключ уже
    закреплён за `request_id`, считался доказательством, что кода нет, — и
    заказ уходил к резервному поставщику, сжигая второй ключ. Правило
    переписано: к резервному уходим только по однозначному `out_of_stock`.
  - **потеря оплаты.** Если вебхук и создание заказа шли одновременно,
    припаркованное событие помечалось обработанным и не применялось уже
    никем: 9 заказов из 150 остались оплаченными без выдачи. Парковка
    перестала считаться завершением обработки.
  - **обход лимита промокода.** Отказ оплаты возвращал использование в лимит,
    а подтверждение платежа, пришедшее позже, оживляло заказ со скидкой, не
    занимая слот заново: код с `max_uses = 1` применялся сколько угодно раз.

  Каждый дефект закрыт, на каждый есть регрессионный тест (у первых двух
  красный-зелёный проверен возвратом бага) и живой сценарий в `make race-all`.
  Это и есть причина, по которой проверка разнесена на независимые проходы:
  автор кода и автор проверки не должны совпадать — ни человек, ни агент.

Ориентировочное распределение: 1.5 часа — надёжность выдачи и состязательные
сценарии, 1 час — витрина и интерактив, 1 час — инфраструктура и заглушки
поставщиков, 0.5 часа — тесты и описание решений.
