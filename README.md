# Магазин цифровых товаров — тестовое задание

Витрина и бэкенд магазина ключей, пополнений, подписок и подарочных карт.
Задача решалась вокруг главного требования: **ключ выдаётся ровно один раз**
при двойных кликах, повторных и одновременных вебхуках, а сбои переводят заказ
в восстановимое состояние, а не роняют систему.

**Второй этап** добавляет живое состояние витрины: цена и остаток переехали с
товара на предложение конкретного продавца, изменения видны во всех открытых
вкладках без перезагрузки, за последнюю единицу товара покупатели конкурируют
по-настоящему, бронь живёт по таймеру, а поиск по каталогу в тысячи
предложений отвечает по мере ввода. **Подробности — в разделах ниже, начиная с
«Что добавил второй этап».**

- **Бэкенд:** PHP 8.3, Laravel 12, PostgreSQL 16, очередь на базе, php-fpm за nginx
- **Фронтенд:** TypeScript + Vite, без фреймворка, SCSS
- **Инфраструктура:** Docker Compose — приложение, воркер, планировщик, SSE-стример живой витрины, база, nginx и два независимых поставщика

## Запуск

Нужен только Docker (PHP и Node на хосте не требуются — фронт собирается в контейнере).

```bash
make up
```

Команда сама создаёт `backend/.env` из шаблона, генерирует ключ приложения,
собирает витрину, поднимает контейнеры и накатывает схему с данными из ТЗ.

После запуска:

| что | адрес |
|---|---|
| витрина | http://localhost:8085 |
| каталог с поиском (второй этап) | http://localhost:8085/catalog.html |
| админка «оплачено, но не выдано» + управление предложениями | http://localhost:8085/admin/orders?token=admin-secret-token |
| живой поток витрины (SSE, для отладки) | http://localhost:8085/api/stream?topics=catalog |
| склад поставщика A | http://localhost:8086/inventory |
| склад поставщика B | http://localhost:8087/inventory |

Каталога из 12 позиций ТЗ достаточно для живого обновления и гонки за
последнюю единицу (см. ниже). Для проверки поиска на объёме нужен отдельный
сид: `make seed-catalog` (около 1600 позиций, около 4000 предложений; склады
поставщиков докупаются под этот объём автоматически). Он не входит в `make up`
и не используется тестами — иначе каждый прогон тестов пересевал бы тысячи
строк заново.

Остальные команды: `make help`.

## Как воспроизвести проверку гонок

```bash
make race-all
```

Команда пересоздаёт схему, засевает исходные данные из ТЗ, возвращает склады
поставщиков и остатки предложений в начальное состояние и прогоняет
тринадцать состязательных сценариев (124 проверки). Каждый сценарий печатает
PASS/FAIL по каждой проверке, в конце — сводная таблица. Отдельный сценарий
запускается своей целью, например `make race-timeout-leak` или
`make race-last-unit`.

Сценарии расходуют пул ключей, лимиты промокодов и остаток предложений,
поэтому перед ручной демонстрацией витрины состояние стоит вернуть в исходное:
`make fresh` (чистая схема, данные ТЗ, склады поставщиков заново) или
`make demo-live`, если демонстрация — про живое обновление и гонку (см. ниже).

Параллельность настоящая: запросы залпа уходят одним `curl_multi`-хэндлом
одновременно, а не по очереди. Проверки идут не по «средним» счётчикам, а по
конкретному заказу и по конкретной строке `stock_units`: у поставщика
спрашивается, сколько ключей закреплено за его `request_id`, у базы — сколько
строк физически лежит в состоянии `reserved`/`sold`, и эти числа обязаны
совпасть с ожиданием буквально, а не «в среднем».

| сценарий | что проверяет | критерий ТЗ |
|---|---|---|
| `race-double-click` | 20 одновременных заказов с одним `Idempotency-Key` → один заказ | двойной клик «Купить» |
| `race-webhook-same-event` | 50 одновременных вебхуков с одним `event_id` | 1, 2 |
| `race-webhook-distinct-events` | 50 одновременных вебхуков с разными `event_id` по одному заказу | 1 |
| `race-out-of-order` | вебхук раньше заказа; устаревшее и запоздавшее события | 3 |
| `race-empty-pool` | пустой склад → восстановимое состояние → пополнение → 10 одновременных повторных выдач | 4 |
| `race-promo-limit` | `ONCEONLY` и `LIMIT3` под 50 одновременными заказами | 5 |
| `race-timeout-leak` | поставщик выдал код, но ответ не дошёл | ловушка таймаута из контракта |
| `race-error-after-issue` | поставщик закрепил ключ и ответил `503` при полном складе резервного | ловушка таймаута из контракта |
| `race-last-unit` | 20 одновременных покупателей на предложение с одной единицей | 2.1, 2.2, 2.3 |
| `race-reservation-expiry` | оплата встречается «нос в нос» с истечением брони, 30 повторов | 3.2, 3.3, 6.4 |
| `race-reserve-vs-expire` | 10 покупателей против снятия брони на предложении с двумя единицами | 3.4 |
| `race-price-change-at-pay` | цена меняется в момент оплаты, 30 повторов | 1.3 |
| `race-stream-catchup` | обрыв SSE-соединения в середине серии изменений, реконнект по `Last-Event-ID` | 1.4 |

Модульные и функциональные тесты: `make test` (139 тестов, 673 проверки).
Они идут на PostgreSQL, потому что схема и логика опираются на его возможности —
частичные уникальные индексы, `FOR UPDATE SKIP LOCKED`, `ON CONFLICT`,
`LISTEN`/`NOTIFY`, триграммный поиск.

## Чем обеспечена однократная выдача

Коротко: **гарантии живут в ограничениях базы, а не в проверках на уровне кода.**
Однократность не зависит ни от порядка запросов, ни от числа воркеров, ни от того,
сколько раз платёжная система повторит доставку.

| ограничение | что закрывает |
|---|---|
| `orders.idempotency_key UNIQUE` | двойной клик «Купить» даёт один заказ: вторая вставка уходит в конфликт, и клиент получает тот же заказ |
| `payment_events.event_id PRIMARY KEY` | повторный вебхук не доходит до бизнес-логики вообще |
| `SELECT ... FOR UPDATE` на заказе + машина состояний | из `created` выйти может ровно одно из параллельных событий |
| `deliveries.order_id UNIQUE` | на заказ приходится максимум одна выдача |
| `deliveries.request_id UNIQUE` + карта `request_id → код` у поставщика | повтор после сбоя возвращает тот же код, а не расходует второй ключ |
| `keys.request_id UNIQUE` в базе поставщика | один ключ физически не может быть закреплён за двумя запросами |
| частичный `UNIQUE (delivered_code)` | один код не может оказаться в двух заказах магазина |
| `UPDATE promocodes SET used_count = used_count + 1 WHERE used_count < max_uses` | лимит промокода соблюдается по числу затронутых строк, без «прочитать-сравнить-записать» |

### Ловушка таймаута

Самое тонкое место задания. Уйти к резервному поставщику можно **только по
однозначному ответу «ключей нет»** (`out_of_stock`). Всё остальное — таймаут,
`5xx`, недоступность, непонятная причина — это неизвестность: код мог быть уже
закреплён за `request_id`, а ответ его не донёс. Переход к резервному в такой
ситуации израсходовал бы **второй ключ**, поэтому он запрещён: заказ уходит в
восстановимое состояние, а повторы идут тому же поставщику с тем же
`request_id`, пока он не ответит внятно.

Соблазнительное правило «ответ получен, кода в нём нет — значит кода не
существует» **неверно**, и это ровно та ошибка, которую нашло состязательное
ревью: поставщик может закрепить ключ и упасть уже на ответе. Заглушка это
воспроизводит режимом `issue_then_error`, и до правки за одним заказом
оказывалось два ключа — свой и резервного поставщика.

Поведение закрыто тестами (`IssueOrderCodeTest`) и двумя живыми сценариями:
`make race-timeout-leak` (A выдаёт код и не отвечает) и
`make race-error-after-issue` (A закрепляет ключ и отвечает `503`, при этом у
резервного поставщика полный склад).

## Архитектура

```
    браузер
       │  POST /api/orders  (Idempotency-Key)
       ▼
    ┌──────────────┐   вебхук по контракту   ┌──────────────────┐
    │  nginx + app │◄────────────────────────│ эмулятор оплаты  │
    └──────┬───────┘                         └──────────────────┘
           │ статус created → paid, одна строка выдачи, задача в очередь
           ▼
    ┌──────────────┐        POST /issue      ┌──────────────┐
    │    worker    │────────────────────────►│ поставщик A  │ свой склад
    │              │  (тот же request_id)    └──────────────┘
    │              │        только при                        
    │              │      однозначном отказе ┌──────────────┐
    │              │────────────────────────►│ поставщик B  │ свой склад
    └──────┬───────┘                         └──────────────┘
           │ delivered / out_of_stock / delivery_failed
           ▼
    ┌──────────────┐
    │  scheduler   │ раз в минуту дожимает незавершённые события и выдачи
    └──────────────┘
```

Ключевые решения:

- **Вебхук отвечает быстро и почти всегда `200`.** Дубли и нарушенный порядок —
  это норма контракта, а не ошибка. `5xx` возвращается только при настоящем сбое,
  чтобы платёжная система повторила доставку.
- **Выдача асинхронная.** Поставщик по условиям задачи умеет подвисать, а вебхук
  обязан ответить быстро, поэтому обращение к поставщику живёт в очереди.
- **Порядок событий определяется меткой платёжной системы**, а не временем
  доставки вебхука: заказ хранит `last_event_at`, и событие старше применённого
  отбрасывается как устаревшее.
- **Прерванная обработка события доводится до конца.** Если событие записалось,
  а применение упало, повторная доставка не считается дублем — иначе оплата
  потерялась бы навсегда. Такие записи добирает и планировщик.
- **Склады поставщиков лежат в отдельных базах.** Приложение не имеет к пулу
  ключей доступа и ходит только через HTTP-контракт `/issue`.
- **Уникальность задачи в очереди намеренно не используется.** Гарантия должна
  держаться на базе, а не на инфраструктуре очереди: даже при дублировании
  задачи или нескольких воркерах второй ключ не уйдёт.
- **Заказ не «падает».** `out_of_stock` и `delivery_failed` — рабочие состояния,
  из которых выдача продолжается автоматически или вручную из админки.

Статусы заказа и переходы — по модели из ТЗ: `created → paid → delivering →
delivered`, ветки `payment_failed`, `out_of_stock`, `delivery_failed`.
Состояние `delivered` не отменяется ничем.

Второй этап добавляет отдельный процесс для живого канала — он не завязан на
запрос-ответ и не проходит через php-fpm:

```
    браузер (N открытых вкладок)
       │
       │ GET /api/stream?topics=catalog,order:<id>&last_event_id=...
       ▼
     nginx  ◄──────────── SSE, событие за событием ────────────  streamer
                                                        (stream:serve,
                                                         stream_select,
                                                         LISTEN 'storefront')
                                                                ▲
                                                                │ pg_notify (ext-pgsql)
                                                                │
     app / worker / scheduler / admin — где меняются offers/stock_units/orders
     INSERT INTO stream_events(...) + pg_notify('storefront', ...) — ОДНА транзакция
```

Публикация события и изменение данных, которое его породило, — одна
транзакция: PostgreSQL доставляет `NOTIFY` только при коммите, поэтому
подписчик физически не может получить уведомление о строке, которой ему ещё
не видно, и не может пропустить уже закоммиченное изменение. `stream:serve`
— отдельный контейнер, а не ещё один маршрут php-fpm: SSE-соединение живёт
часами, и воркер fpm был бы занят на всё это время — несколько открытых
вкладок проверяющего съели бы пул целиком вместе с обычным API.

## API

| метод | адрес | назначение |
|---|---|---|
| `GET` | `/api/products` | каталог первого этапа (12 позиций), цена — лучшего предложения; плюс `best` и `stream_cursor` |
| `GET` | `/api/catalog` | каталог с поиском, фильтрами, сортировкой и постраничной выдачей (второй этап) |
| `GET` | `/api/offers?sku=` | все активные предложения позиции — для альтернативы и списка продавцов |
| `POST` | `/api/orders` | создание заказа по `offer_id` (или `sku` — выбор лучшего предложения), обязателен заголовок `Idempotency-Key` |
| `GET` | `/api/orders/{id}` | статус, бронь, выданный код и история переходов |
| `POST` | `/api/orders/{id}/reprice` | принять изменившуюся цену предложения до оплаты |
| `POST` | `/api/webhook/payment` | вебхук платёжной системы по контракту ТЗ |
| `POST` | `/api/dev/pay/{id}?result=success\|fail` | эмулятор оплаты: формирует событие и отправляет вебхук |
| `POST` | `/api/dev/orders` | заказ с заранее известным id — только для сценария «вебхук раньше заказа», недоступно в production |
| `POST` | `/api/dev/reservations/{id}/expire` | просрочить бронь заказа немедленно, не дожидаясь TTL |
| `GET` | `/admin/orders?token=` | список «оплачено, но не выдано» + управление предложениями |
| `POST` | `/admin/orders/{id}/redeliver` | безопасная повторная выдача, включая заказы с пометкой «требуется возврат» |
| `POST` | `/admin/suppliers/{a\|b}/restock` | пополнение склада поставщика |
| `POST` | `/admin/offers/{id}/price` | изменить цену предложения |
| `POST` | `/admin/offers/{id}/stock` | выставить остаток свободных единиц |
| `POST` | `/admin/offers/{id}/toggle` | скрыть/показать предложение |
| `POST` | `/admin/offers/{id}/leave-one` | оставить ровно одну свободную единицу (подготовка гонки) |

Живой канал `/api/stream?topics=...&last_event_id=...` — не маршрут Laravel:
nginx проксирует его напрямую в отдельный процесс `stream:serve` (см.
«Архитектура»), php-fpm в этом пути не участвует вовсе.

Поставщики (заглушки по контракту ТЗ): `POST /issue`, `GET /inventory`,
`GET /issued/{request_id}`, `POST /restock`, `POST /drain`, `POST /reset`,
`POST /config` — последняя задаёт долю отказов, таймаутов и режим
«выдал код, но не ответил».

## Витрина

ТЗ просило верхнюю часть до первого ряда карточек. Сверстана страница целиком —
шапка, баннер-карусель, ряд иконок сервисов, блок пополнения Steam, три ряда
карточек товара, блок последних отзывов и футер: отзывы и футер сделаны сверх
задания, по своей инициативе.

Значения не подбирались на глаз — размеры, отступы, радиусы, тени, шрифты и
цвета взяты из макета через Figma MCP (design context) по каждому узлу.
Контрольные точки после вёрстки совпадают с макетом: полотно 1280, контейнер
1200, шапка 80 с границей `#f2f4f7`, кнопка каталога 232/18 120×44, поиск
428/18 688×44 (чёрная подложка и белое поле 642×40 внутри), профиль 1196/18
44×44, баннер 40/96 1200×263, пилюля стрелок 1150/96 90×40, блок сервисов
40/375 1200×253, плитка иконки 72×72 в обёртке 76 с брендовой рамкой 2px,
разделитель 1160×1 на y=519, ряд пополнения 285.51 / 284.77 / 341.72 / 200,
карточка 227.27 с медиа 151.72, отзыв 389.33, футер 1200×234.

Шрифт макета — Montserrat. Он лежит в репозитории (вариативный woff2,
кириллица и латиница, 60 КБ) и не тянется с внешнего CDN, поэтому витрина
одинаково выглядит и без интернета. Иконки — экспортированные из Figma SVG и
PNG, пережатые в webp; ничего не перерисовано вручную.

Меню каталога сверстано по второму скриншоту ТЗ: панель во всю ширину полотна,
сайдбар 320 с активной категорией, пять колонок платформ по 137.6 с гапом 32 и
вторым рядом «Подборки».

Обязательный интерактив (номера со скриншота ТЗ):

1. **Баннер-карусель** — автопрокрутка, стрелки, активная точка-индикатор;
   пауза при наведении и при уходе со вкладки, уважает `prefers-reduced-motion`.
2. **Кнопка «Каталог»** — открывает меню, закрывается повторным кликом, кликом
   вне меню и клавишей Escape. Вид поиска при этом не меняется: в макете
   закрытое и открытое состояния шапки идентичны.
3. **Переключатель валют `$ ₸ ₽`** — меняется активное состояние; пересчёт
   суммы, по ТЗ, не делается.
4. **Иконки сервисов** — плавное выделение при наведении.
5. **Карточки товара** — подъём, тень и обводка при наведении.

Покупка начинается кнопкой «Купить» на карточке: фронт создаёт заказ с ключом
идемпотентности и уводит на страницу статуса, которая опрашивает API (интервал
растёт до 5 секунд, опрос замолкает на скрытой вкладке) и показывает выданный
код и историю переходов.

Промокод этапа 4 живёт там, где он есть в макете: кнопка «Ввести промокод» в
блоке пополнения Steam раскрывает поле, а кнопка «Оплатить» покупает товар
каталога `STEAM-TOPUP-500` — именно этот номинал нарисован в блоке. Скидку
считает сервер, клиент присылает только код; отказ по коду («не найден»,
«лимит исчерпан») показывается у поля.

## Что добавил второй этап

Первый этап держал цену и наличие на самом товаре, а «склад» был общим пулом
ключей у поставщика, не привязанным к конкретной позиции каталога — магазин
узнавал, что товара нет, только постфактум, по ответу поставщика. Второй этап
убирает это допущение: цена и остаток переехали на **предложение** конкретного
продавца (`offers`), а сам остаток — это не число, а строки `stock_units`, по
одной на физическую единицу товара. У одной позиции каталога может быть
несколько предложений разных продавцов по разным ценам; «единица» — это
конкретная строка, которую можно захватить, забронировать и продать ровно
один раз.

По пяти задачам ТЗ, коротко:

1. **Живая витрина.** Любое изменение цены, остатка или видимости
   предложения публикуется событием в журнал `stream_events` и рассылается
   через `pg_notify` всем открытым вкладкам по SSE (`/api/stream`) — без
   опроса и без перезагрузки страницы. Работает на витрине, на странице
   поиска и на странице заказа. Если предложение подорожало (или подешевело),
   пока заказ ждал оплаты, это видно до оплаты, а не после: сервер отказывает
   `409 price_changed`, пока новая цена не принята явно
   (`POST /api/orders/{id}/reprice`).
2. **Последняя единица наперегонки.** Захват единицы — один
   `UPDATE ... FOR UPDATE SKIP LOCKED` внутри транзакции создания заказа:
   параллельные покупатели физически не могут забрать одну и ту же строку
   `stock_units` дважды. Проигравшим — `409` с предложением другого продавца,
   а не тупик.
3. **Бронь с таймером.** Захваченная единица держится за заказом 300 секунд
   (`RESERVATION_TTL_SECONDS`), на странице заказа идёт видимый отсчёт;
   планировщик каждую секунду снимает истёкшие брони и возвращает единицы в
   продажу — с уведомлением всех открытых вкладок тем же событийным каналом.
4. **Устойчивость покупки.** Оплата, пришедшая после истечения брони, не
   теряется: единица либо ещё держится за заказом и продаётся, либо
   перезахватывается другая единица того же предложения по той же цене, либо
   — если единиц действительно не осталось — заказ помечается «требуется
   возврат» и виден в админке (подробнее — в разделе «Бронь: что происходит
   на границе» ниже). Плюс: страница заказа переживает «Назад» из истории
   браузера и обрыв связи со стримером.
5. **Мгновенный поиск.** Каталог на ~1600 позиций и ~4000 предложений ищется
   триграммным индексом PostgreSQL по мере ввода; на фронте — отмена
   устаревшего запроса и монотонный счётчик против гонки ответов, список не
   очищается во время загрузки, фильтры сохраняются в адресе страницы.

## Демонстрация второго этапа

Формат ответа ТЗ прямо просит показать, как воспроизвести живое обновление и
гонку за последнюю единицу — ниже пошагово: что запустить, что открыть и что
именно смотреть.

### Живое обновление витрины

1. Подготовить стенд:

   ```bash
   make demo-live
   ```

   Команда пересоздаёт схему, засевает данные ТЗ, возвращает остатки в
   исходное состояние, дожидается первого тика планировщика (см. ловушку
   ниже) и печатает адреса витрины и админки.

2. Открыть витрину в двух вкладках браузера: http://localhost:8085/ — обе
   покажут одинаковый список карточек, среди них «CS2 Prime Status ключ»
   (`KEY-CS2-PRIME`). У его самого дешёвого предложения на свежем сиде ровно
   одна единица в продаже — то же предложение нужно и для гонки ниже.
3. Открыть третью вкладку — админку:
   http://localhost:8085/admin/orders?token=admin-secret-token. В блоке
   «Управление предложением» нужен id предложения; на практике на свежем сиде
   это `8` — проверить можно так:

   ```bash
   curl -s "http://localhost:8085/api/offers?sku=KEY-CS2-PRIME"
   ```

   (нужен первый элемент ответа — самая низкая цена).
4. **Смена цены (1.1).** В форме «Изменить цену» ввести offer id и новую цену
   в копейках (например, `199000` = 1990 ₽), нажать «Изменить цену». Обе
   вкладки витрины обновляют цену карточки без перезагрузки — в измерениях на
   стенде это занимало 30–130 мс.
5. **Остаток дошёл до нуля (1.2).** В форме «Задать остаток» ввести тот же
   offer id и `0`, нажать «Задать остаток». Кнопка «Купить» на карточке в
   ОБЕИХ вкладках гаснет одновременно («Нет в наличии»). Вернуть — тот же
   offer id и `units=1` (или больше). То же самое видно и через гонку — см.
   следующий раздел.
6. **Цена видна до оплаты (1.3).** Купить любой товар в одной из вкладок
   (уводит на страницу заказа с активной бронью), затем в админке изменить
   цену именно этого предложения. На странице заказа появляется плашка «Цена
   изменилась: X ₽ → Y ₽» с кнопкой «Оплатить по новой цене»; обычная оплата
   недоступна, пока цена не принята.
7. **После обновления и обрыва связи (1.4).** Обновить (F5) любую из вкладок
   — актуальные цена и остаток видны сразу, ещё до первого события (сервер
   отдаёт их в снапшоте). Чтобы увидеть именно реконнект: `docker compose
   stop streamer`, поменять что-нибудь в админке (событие никуда не уйдёт —
   стример не слушает), затем `docker compose start streamer` — открытые
   вкладки переподключаются сами (задержки 1→2→4→8→15 с) и подтягивают
   пропущенное без обновления страницы.
8. Ускорить бронь, не дожидаясь 300 секунд:

   ```bash
   curl -s -X POST http://localhost:8085/api/dev/reservations/ord_XXXX/expire
   ```

   Ручка переставляет дедлайн брони в прошлое; фактическое снятие (и событие
   всем вкладкам) выполняет ближайший тик планировщика — обычно в течение
   секунды, если планировщик уже «прогрет» (см. ловушку ниже).

### Гонка за последнюю единицу

1. Убедиться, что у предложения ровно одна свободная единица — после
   `make demo-live`/`make fresh` это уже так для `KEY-CS2-PRIME`; вручную —
   кнопка «Оставить одну единицу» в админке по offer id.
2. Не обязательно, но нагляднее: открыть карточку этого товара в одной-двух
   вкладках витрины, чтобы увидеть, как кнопка «Купить» гаснет в реальном
   времени сразу после гонки.
3. Запустить:

   ```bash
   make race-last-unit
   ```

4. Реальный прогон на этом стенде (сокращено):

   ```
   Последняя единица: 20 одновременных покупателей на одно предложение
   -------------------------------------------------------------------
     · оставляем у предложения 8 (цена 129000) ровно одну свободную единицу
     PASS у позиции KEY-CS2-PRIME есть второе активное предложение для альтернативы
     · залп из 20 POST /api/orders на offer_id=8, разные Idempotency-Key
     PASS ровно один ответ 201
            201: 1
     PASS остальные 19 получили 409 sold_out
            409 sold_out: 19
     PASS у каждого отказа непустая альтернатива с available > 0
     PASS в stock_units предложения ровно одна строка в состоянии reserved
     PASS этим залпом создан ровно один новый заказ
     · оплачиваем победителя
     PASS после оплаты победитель выдан
     PASS единица победителя перешла в состояние sold
     PASS ни один проигравший так и не получил заказ на это предложение (2.1, 2.2, 2.3)

     Итог: 12 из 12 проверок пройдено. СЦЕНАРИЙ ПРОЙДЕН
   ```

5. **Почему это доказательство, а не иллюстрация.** Сценарий сам поднимает
   предложение до одной свободной единицы (не полагается на состояние
   стенда) и шлёт 20 запросов `POST /api/orders` ОДНИМ залпом (`curl_multi`,
   действительно одновременно, а не по очереди) с разными
   `Idempotency-Key` на один и тот же `offer_id`. Проверяются не «средние»
   показатели, а точные числа из ответов и из базы: ровно один `201`, ровно
   19 `409 sold_out` с непустой альтернативой у каждого, ровно одна строка
   `stock_units` в состоянии `reserved` у победителя, ровно один новый заказ
   на это предложение. Дальше сценарий оплачивает победителя и проверяет, что
   ни один из 19 проигравших так и не получил заказ на этот же товар.

   Главное же — сценарий проверен «в обе стороны». Если убрать
   `FOR UPDATE SKIP LOCKED` из `StockService::reserve()` (оставить голый
   `UPDATE ... LIMIT 1`), тот же сценарий ловит **два** `201` вместо одного и
   падает:

   ```
     FAIL ровно один ответ 201
            201: 2
     FAIL этим залпом создан ровно один новый заказ
            новых заказов: 2
     FAIL ни один проигравший так и не получил заказ на это предложение (2.1, 2.2, 2.3)
            новых заказов: 2

     Итог: 8 из 12 проверок пройдено. СЦЕНАРИЙ ПРОВАЛЕН
   ```

   То есть сценарий действительно проверяет то самое ограничение, которое
   обеспечивает гарантию 2.1–2.3 ТЗ, а не просто повторяет ожидаемый ответ.

### Две ловушки демонстрации

Демонстрация проходит гладко почти всегда, но два эффекта легко принять за
поломку, если не знать о них заранее.

**Планировщик после рестарта молчит до минуты.** `schedule:work` для
секундных задач (`everySecond()`, на нём держится снятие истёкшей брони) при
холодном старте не тикает сразу — он ждёт ближайшую границу минуты и только
тогда начинает секундный цикл. Если сразу после `docker compose restart
scheduler` (или `make restart`, которая перезапускает его тоже) просрочить
бронь и сразу смотреть на витрину, простой может доходить до ~59 секунд, и
это легко принять за «механизм не работает», хотя он просто ещё не проснулся.
`make demo-live` не перезапускает `scheduler` — использует уже тикающий
контейнер и сам ждёт первый тик в его логах, прежде чем сказать «стенд
готов». Если `scheduler` перезапускали вручную непосредственно перед
демонстрацией — стоит подождать или посмотреть `docker compose logs -f
scheduler`, пока не появится первая строка про `reservations:release`.

**Пересборка стримера — окно ~10 секунд на 502.** nginx резолвит адрес
контейнера `streamer` через встроенный DNS докера с кэшем `valid=10s` —
специально, чтобы уметь пережить пересоздание контейнера, не упав самому.
Если стример пересобрать (`docker compose up -d --build streamer`, а не
обычный `restart`, который адрес контейнера не меняет), то в течение
следующих примерно 10 секунд НОВОЕ подключение к `/api/stream` может
получить `502`, пока nginx не перерезолвит адрес — уже открытые до этого
соединения такую пересборку не замечают. Если вкладка витрины открывается
именно в эту паузу — достаточно обновить страницу через несколько секунд, а
не считать живую витрину сломанной.

## Критерии приёмки второго этапа

Таблица по всем пяти задачам ТЗ: что конкретно держит гарантию (ограничение
базы или серверная проверка, а не общие слова «проверено в коде») и чем это
подтверждено.

| требование | чем обеспечено | чем проверено |
|---|---|---|
| 1.1 живое обновление во всех вкладках | `stream_events` + `pg_notify` в одной транзакции с изменением данных; SSE (`stream:serve` на `stream_select`); точечное применение по `offer_id` без перерисовки списка | две вкладки + админка (см. демонстрацию); `race-stream-catchup` |
| 1.2 кнопка гаснет у всех при остатке 0 | `available` в payload события — то же число, что и в снапшоте каталога | `race-last-unit` при открытых вкладках |
| 1.3 новая цена видна до оплаты | сервер сверяет `offers.price_minor` с `orders.amount_minor` перед вебхуком, отказ `409 price_changed`; `POST /reprice` явно принимает новую цену | `race-price-change-at-pay`; вручную — сменить цену при открытой странице заказа |
| 1.4 работает после обновления и обрыва | снапшот отдаёт `stream_cursor`; реконнект по `Last-Event-ID` дочитывает хвост журнала ДО перехода в живой режим; курсор непрерывности переживает обгон `bigserial`-id | `race-stream-catchup` |
| 2.1 последнюю единицу получает один | `UPDATE ... FOR UPDATE SKIP LOCKED` по строке `stock_units` внутри транзакции заказа | `race-last-unit`, включая red/green без `SKIP LOCKED` (см. выше) |
| 2.2 понятный отказ с альтернативой | `409 sold_out` несёт `alternative` — другое активное предложение той же позиции | `race-last-unit`; тост на витрине |
| 2.3 нет оплаченных заказов без товара | продажа единицы — часть применения оплаты (`sellForOrder`): держит свою единицу, перезахватывает чужую свободную или помечает `refund_required`, но никогда не переводит в `paid` без единицы | `race-last-unit`, `race-reservation-expiry` |
| 3.1 видимый отсчёт брони | `reservation.expires_at` в ответе API, клиентский таймер на странице заказа | глазами |
| 3.2 бронь снимается и товар возвращается всем | планировщик `ReleaseExpiredReservations` (`everySecond`), событие `offer.updated` по каждому освобождённому предложению | `race-reservation-expiry`; `POST /api/dev/reservations/{id}/expire` |
| 3.3 оплата успела — бронь больше не влияет | `sellForOrder` продаёт единицу, закреплённую за заказом, даже если `reserved_until` формально в прошлом — кто раньше оказался в базе, тот и прав | `race-reservation-expiry` |
| 3.4 товар не бронируется под два заказа | частичный `UNIQUE (reserved_order_id) WHERE reserved_order_id IS NOT NULL` на `stock_units` | `race-reserve-vs-expire` |
| 4.1 не задваивает заказ/оплату | `orders.idempotency_key UNIQUE` + `ON CONFLICT DO NOTHING`; `payment_events.event_id` теперь детерминирован (`evt_<заказ>_<результат>_<попытка>`) | `race-double-click`, `race-webhook-same-event` |
| 4.2 верный статус после «Назад»/обрыва | страница заказа слушает SSE-топик `order:<id>` (опрос — фоллбэк, если поток не открылся); `pageshow` + `event.persisted` перезапрашивает заказ, если браузер отдал его из bfcache | вручную: оплатить → «Назад» |
| 4.3 повторная оплата ничего не меняет | `payment_events.event_id` в первичном ключе + машина статусов заказа | `race-webhook-same-event`, `race-webhook-distinct-events` |
| 5.1 без задержек и мигания | debounce 120 мс на ввод; сетка каталога обновляется точечным diff по `offer_id`, а не полной перерисовкой | глазами на `make seed-catalog`; замеры 16–90 мс на запрос |
| 5.2 устаревший ответ не перетирает свежий | `AbortController` отменяет предыдущий запрос; монотонный счётчик запросов — страховка на случай, если отменённый запрос всё же успеет вернуться | инженерный опыт с намеренно отключённым `abort()`: ответ, пришедший на 566 мс позже свежего, всё равно отброшен по счётчику |
| 5.3 фильтры в адресе, открываются по ссылке | `history.replaceState` при каждом изменении фильтров, восстановление при загрузке страницы и на `popstate` | вручную — прямая ссылка с `?q=&type=&page=` |

## Бронь: что происходит на границе

Заказ резервирует ровно одну физическую строку `stock_units` на 300 секунд.
Самое интересное происходит, когда оплата подтверждается ПОСЛЕ того, как этот
срок формально истёк — вебхук платёжной системы не спрашивает, тикнул ли уже
планировщик. Обработка оплаты разбирает три исхода, в этом порядке:

1. **Единица ещё за заказом.** Планировщик просто не успел добежать до этой
   строки — она физически всё ещё числится `reserved` за этим заказом. Тогда
   она продаётся немедленно, НЕЗАВИСИМО от того, что таймер на экране уже
   показал бы «Бронь истекла»: побеждает то, что реально лежит в базе, а не
   то, что успели отсчитать браузер или разослать планировщик. Покупатель не
   отвечает за секундную задержку служебного процесса.
2. **Единицу успели забрать.** Планировщик уже освободил строку (или её
   перехватил кто-то, кто пришёл за ней позже, — см. `race-reserve-vs-expire`).
   Тогда сервер пробует захватить ДРУГУЮ свободную единицу того же
   предложения — по уже уплаченной цене, её задним числом не меняют.
   Получилось — заказ уходит в оплаченные и в выдачу, как будто ничего не
   случилось, только «под капотом» единица другая.
3. **Единиц не осталось вовсе.** Не повезло: все единицы предложения к этому
   моменту разошлись другим покупателям. Деньги пришли, а продавать нечего —
   заказ помечается `out_of_stock` с `refund_required = true` и попадает в
   тот же список админки «оплачено, но не выдано», что и заказы с ошибкой
   выдачи от поставщика. Автоматического возврата денег или автоматического
   дозахвата здесь нет (см. «Допущения») — но как только администратор
   пополнит остаток предложения, та же кнопка «Выдать повторно» в админке
   умеет закрыть именно эту брешь: захватить свободную единицу по уже
   уплаченной цене и довести заказ до выдачи.

Разрешённые исходные статусы для перехода в `paid` — `created`,
`payment_failed` и, специально ради этой картины, `reservation_expired`:
деньги, которые уже пришли, нельзя терять только потому, что бронь формально
кончилась раньше, чем добежал вебхук. Симметрично: если платёж, наоборот,
приходит с результатом «отказано» уже после того, как бронь истекла,
обработчик ничего не меняет — заказ уже мёртв, а слот промокода, если он был
занят, к этому моменту уже сгорел вместе с истёкшей бронью (слот принадлежит
заказу, а не попытке оплаты — то же правило, что и в первом этапе).

## Допущения

- Пул из 50 ключей ТЗ универсален: сопоставления `sku` → ключ в задании нет.
  Пул поделён между поставщиками, A получает 30 ключей, B — 20; доли задаются
  переменными `KEYS_OFFSET` и `KEYS_LIMIT`.
- Деньги хранятся целыми в копейках (`*_minor`), без чисел с плавающей точкой.
  Цену и скидку клиент не присылает никогда — только `sku` и промокод.
- Промокод занимает использование в момент создания заказа и **не освобождает
  его при неуспешной оплате**. Это осознанный выбор: платёж может подтвердиться
  позже (заказ обязан ожить, иначе оплата теряется), и если слот к тому времени
  уйдёт другому покупателю, код окажется применён больше `max_uses` раз. Слот
  принадлежит заказу, а не попытке оплаты: повторная оплата того же заказа
  сохраняет скидку. Цена решения — брошенный неоплаченный заказ держит своё
  использование; `make fresh` возвращает лимиты в исходное состояние.
- Вебхук на несуществующий заказ получает `200` и паркуется: восстановлением
  владеет магазин, заставлять платёжную систему повторять доставку незачем.
  Припаркованное событие **не считается обработанным** — его применяет либо
  создание заказа, либо планировщик, когда заказ появится. Иначе гонка
  «вебхук и создание заказа одновременно» теряла бы оплату.
- Порядок событий определяет метка платёжной системы, а в контракте она с
  секундной точностью. На ничьей побеждает `paid`: потерять деньги хуже, чем
  лишний раз оживить заказ, а оживление безопасно.
- Рассинхрон валют в блоке Steam (сумма в ₽, кнопка в $) оставлен как в макете —
  ТЗ просит его не исправлять.
- Зачёркнутая цена на карточке декоративная: старой цены в данных ТЗ нет,
  она считается от текущей, чтобы не ломать вёрстку.
- Каталог ТЗ содержит 12 товаров, а в макете три ряда по пять карточек,
  поэтому ряды заполняются по кругу — три плитки повторяются.
- Названия карточек оформлены эмодзи-акцентами, как в макете
  (`💥 DOOM 2016 💀 STEAM KEY 🔑`), но по названиям товаров из каталога ТЗ.
  Квалификатор вроде «STEAM KEY» не добавляется: с ним ни одно название
  каталога не влезает в строку 200.92px, а в макете название занимает одну
  строку, регион — вторую.
- Один код не может оказаться в двух заказах: это частичный `UNIQUE` по
  `delivered_code`. Если поставщика заставить вернуть код, уже привязанный к
  другому заказу (штатно так делает только `POST /reset` заглушки, который
  возвращает выданные ключи в сток), выдача такого заказа будет падать на
  ограничении — состояние лечится общим сбросом `make fresh`.
- Баннер в макете пустой, готового арта нет ни в исходнике, ни на скриншотах.
  Слайды собраны кропами имеющегося изображения и описаны данными
  (`frontend/src/data/slides.ts`) — тематические баннеры подставляются заменой
  путей, без правки вёрстки.
- Контейнеры приложения запускаются под текущим пользователем (`make` передаёт
  `id -u`/`id -g`), чтобы `storage/` оставался доступен для записи и на хосте,
  и в контейнере.
- Топик `catalog` получает события по ВСЕМ предложениям, а не только по тем,
  что видны в текущей выдаче поиска или на экране конкретной вкладки; клиент
  отбрасывает лишнее гардом по версии. На объёме этого этапа (события рождают
  только покупки и админка) лишний трафик не заметен, а фильтрация по
  подписке усложнила бы переоткрытие потока при каждой смене фильтра поиска.
  В продакшне это был бы отдельный топик на срез каталога.
- Одна открытая вкладка — одно SSE-соединение к стримеру (лимит — 200
  одновременных, см. «Две ловушки демонстрации» про причины лимита). Пять
  вкладок — пять соединений. Продакшн-путь — один `SharedWorker` на весь
  браузер с одним соединением на все вкладки; для проверки требования «во
  всех вкладках» это лишний слой, который ничего не доказывает дополнительно.
- Учёт магазина (`stock_units`) и склад поставщика — два независимых числа,
  синхронизированные сидом на старте. Расхождение (например, через `/drain`
  у поставщика) не подвисает: заказ на такую позицию просто уходит по ветке
  `out_of_stock`, как и в первом этапе, и её же реконсилятор
  (`ReconcileDeliveries`, раз в минуту) дожимает то, что зависло.
- Возврата денег нет — реального эквайринга в задании нет, а без него
  возврат нечего дёргать по-настоящему. Заказ, оплата по которому
  подтвердилась, а товара не осталось, помечается `refund_required = true` и
  виден в админке отдельным признаком; закрывает его администратор — либо
  пополнением остатка и повторной выдачей, либо возвратом денег вне системы.
  Автоматического пути здесь нет и не планируется.
- Поиск — не про миллион позиций. На ~4000 предложениях `ILIKE` по
  триграммному индексу и постраничный `count(*)` отвечают за миллисекунды;
  для каталога на порядки крупнее понадобился бы отдельный поисковый индекс —
  упрётся сначала именно пагинация (`count(*)` на каждый запрос) и посимвольный
  `ILIKE`, а не сама триграмма.

## Что не делалось

По прямым указаниям ТЗ: реальный эквайринг, проверка подписи вебхука,
авторизация (у админки простой токен), мобильная и тёмная версии, дизайн
страницы статуса и админки, пересчёт валют.

Второй этап по тем же указаниям ТЗ не трогает вёрстку и интерактив первого
этапа, отзывы и футер (ТЗ прямо говорит, что они не нужны, а из первого этапа
они уже есть); страница поиска нового каталога вне макета ТЗ, поэтому её
пиксель-перфектом никто не мерил. Сверх того — осознанно вне объёма:
автоматический возврат денег и автоматическое восстановление заказов с
пометкой «требуется возврат» (оба — только вручную, из админки; подробнее —
в «Допущения»), фильтрация SSE-топика по подписке, общий `SharedWorker` на
вкладку, поиск на каталоге масштаба миллионов позиций.

## Как это сделано

Скорость работы здесь — следствие инструментов и организации, а не срезанных
углов, поэтому ниже прямо описано, как задача делалась.

Инструмент — **Claude Opus 5** в режиме агентного воркфлоу: не «сгенерируй
магазин», а несколько управляемых потоков с моей постановкой, приёмкой и
правками на каждом шаге. Архитектурные решения — где живёт гарантия
однократности, что держит база, а что код — мои, и я отвечаю за каждое.

- **Постановка до кода.** Сначала брейншторм требований и рисков:
  однократная выдача, ловушка таймаута поставщика, порядок вебхуков, лимит
  промокода под параллелизмом. Спецификация, модель статусов и план по
  этапам согласованы до первой строки кода.
- **Оркестрация вместо линейной разработки.** Независимые части — схема и
  ограничения PostgreSQL, заглушки поставщиков, витрина, состязательные
  скрипты — шли параллельными потоками по общей спецификации, с профильным
  агентом на каждый слой.
- **Вёрстка.** Отдельный агент с заданными скилами, настроенный под
  энтерпрайз-проекты, в которых я работаю: тот же стек, те же соглашения по
  структуре и стилям. Макет читался через **Figma MCP** — размеры, отступы,
  типографика и цвета берутся из узлов макета, иконки экспортируются
  ассетами, а не перерисовываются. Результат сверялся измерениями в
  браузере, а не сравнением скриншотов.
- **Проверка в несколько независимых проходов.** Модульные и функциональные
  тесты (44 теста, 183 проверки), состязательные сценарии (`make race-all` —
  8 сценариев, 74 проверки), затем adversarial-ревью: независимые параллельные
  проходы, чья единственная задача — сломать однократность выдачи,
  восстановление после сбоев и денежную логику. Именно оно поймало три
  дефекта, которых не видели ни тесты, ни состязательные сценарии:
  - **задвоение ключа.** Ответ `503` от поставщика после того, как ключ уже
    закреплён за `request_id`, считался доказательством, что кода нет, — и
    заказ уходил к резервному поставщику, сжигая второй ключ. Правило
    переписано: к резервному уходим только по однозначному `out_of_stock`.
  - **потеря оплаты.** Если вебхук и создание заказа шли одновременно,
    припаркованное событие помечалось обработанным и не применялось уже
    никем: 9 заказов из 150 остались оплаченными без выдачи. Парковка
    перестала считаться завершением обработки.
  - **обход лимита промокода.** Отказ оплаты возвращал использование в лимит,
    а подтверждение платежа, пришедшее позже, оживляло заказ со скидкой, не
    занимая слот заново: код с `max_uses = 1` применялся сколько угодно раз.

  Каждый дефект закрыт, на каждый есть регрессионный тест (у первых двух
  красный-зелёный проверен возвратом бага) и живой сценарий в `make race-all`.
  Это и есть причина, по которой проверка разнесена на независимые проходы:
  автор кода и автор проверки не должны совпадать — ни человек, ни агент.

**Второй этап.** Каждая задача этапа — отдельный коммит, каждый фикс-раунд
ревью — тоже отдельный, ничего не переписано поверх.

Инструмент и подход те же, что в первом этапе, — **Claude Opus 5** в режиме
агентного воркфлоу, не «сгенерируй реалтайм», а управляемые независимые
потоки с моей постановкой и приёмкой на каждом шаге. Модель данных (цена и
остаток переезжают на предложение продавца), семантика гонки за единицу, три
ветки поздней оплаты и разбор каждой находки ревью — мои решения, агенты —
инструмент их реализации и проверки.

- **Постановка до кода.** Модель данных, инварианты на уровне базы (какие
  ограничения PostgreSQL, а не проверки в PHP, обязаны держать каждую
  гарантию), протокол SSE и таблица критериев приёмки — до первой строки
  кода. Отдельно расписана карта пересечений между будущими задачами по
  общим файлам, чтобы решать конфликты заранее, а не по факту слома чужой
  работы.
- **Оркестрация по границам файлов.** Реализация разбита на независимые
  задачи; там, где границы файлов не пересекались (например, SSE-стример —
  параллельно вёрстке каталога поиска и админке), исполнители шли
  одновременно, там, где пересекались — по заранее прописанному порядку.
- **Проверка в несколько независимых проходов.** Модульные и функциональные
  тесты (139 тестов, 673 проверки), состязательные сценарии (`make race-all` —
  13 сценариев, 124 проверки, включая red/green прогон на обеих новых
  гарантиях базы), затем независимое ревью каждой задачи отдельным
  исполнителем — автор кода и автор проверки не совпадали ни разу. За время
  этапа поймано четыре реальных дефекта — не стилистика, а вещи, которые в
  проде сломали бы конкретную гарантию:
  - **тест, «защищавший» оплаченный заказ от планировщика, не проверял
    вообще ничего.** Поймал сам исполнитель, разбираясь, почему тест не
    падает: `RefreshDatabase` держит тест в транзакции, а PostgreSQL
    замораживает `now()` на её старте, и сдвиг часов PHP (`$this->travel()`)
    базе не виден. Тест переписан на перестановку самой метки времени в
    прошлое; это же правило защитило от той же ошибки ещё две следующие
    задачи.
  - **повторный запрос с тем же ключом идемпотентности мог получить ложное
    «раскупили».** Нашло ревью: путь «покупка по sku без явного offer_id»
    переразрешал предложение ДО поиска существующего заказа по ключу — если
    позиция успевала распродаться между двумя вызовами, повторный клик
    получал 409 вместо своего же заказа. Порядок проверок переставлен.
  - **предложение, снятое с продажи, можно было купить по прямой ссылке.**
    Нашло ревью: явный `offer_id` скрытого предложения не блокировался — в
    обход единственного механизма снятия товара с продажи. Добавлена
    проверка видимости.
  - **плашка изменившейся цены не работала, если стример недоступен** —
    ровно в том сценарии устойчивости, ради которого заведён фоллбэк-опрос.
    Нашло ревью: цена для сравнения бралась только из живых событий потока,
    а в режиме опроса её было неоткуда взять. Источник цены расширен на
    снапшот.

  На каждый дефект — регрессионный тест или сценарий, ни один не остался
  только «поймали и обсудили».

На момент сдачи открытыми остаются 20 отложенных замечаний уровня Minor из
ревью — каждое дешёвое само по себе и не блокирует ни один пункт приёмки:
тесты и сценарии выше зелёные. Список веду отдельно и могу показать целиком:
это в основном пробелы покрытия на редких ветках и формулировки комментариев.
